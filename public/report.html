Supabase: the recommended starting point

It combines a hosted database with authentication. An Edge Function could expose the calendar API, verify the owner’s session and check guest-link access before an atomic database operation.

Why localStorage isn’t enough

The existing app saves movies by year in one browser’s storage. That can survive closing and reopening the browser, but it is not a shared database and can be cleared or changed locally.

MDN: localStorage

What a database changes

Two devices request the same calendar record. A successful server write becomes visible when another device fetches fresh data. A separate persistent database can survive an application-server restart; this must still be verified on the chosen host.

A small relational model for this project
users         id  ← identity managed by Supabase Auth
calendars     id, owner_id → users.id, name, year,
              sharing_locked, share_token_hash, version
movies        calendar_id → calendars.id, day, title
              UNIQUE(calendar_id, day)
              CHECK(day BETWEEN 1 AND 24)

One owner → many calendars → 24 movie rows per calendar.

This structure is implemented in the SQL migration. The transaction validates 24 distinct days and saves the list together. The version number rejects an old draft if another person saved first; the concurrency test returned one success and one 409 conflict.

03 / OWNERSHIP, SHARING & THE DEADLINE

Easy to join.
Clear about control.

The central design choice is a shared editing window. The creator owns the calendar, guests help choose movies, and December turns the list into a settled set of surprises.

Use the Vue version

It already has the required interface and reusable components. Reusing it keeps the scope focused on data and access rules.

Let the owner close shared editing early

Before December 1, an unlocked calendar can be edited by the owner and anyone holding its valid guest link. If the owner locks sharing, only the owner can edit.

Close movie editing for everyone on December 1

The owner is included. The earlier suggestion that the owner could edit throughout December was corrected during the discussion.

Use an email sign-in link for owners

Choose movies first; verify an email when saving and sharing. No password or profile form. An owner can return on another device through the same email. Guests use the shared link without signing in.

Keep the new project separate

The teacher clarified that both a working back-end version and a separate report are required. They are built in a new folder. No source changes are made to the original React, Vue, Angular or comparison projects.

Why an email sign-in link?

It balances low friction with recovery. A short permanent calendar PIN is easier to guess or share. A private owner link avoids verification, but anyone with it becomes the owner and losing it can mean losing access. Phone verification still adds a step and needs SMS delivery.

An email sign-in link confirms control of the mailbox, rather than a person’s legal identity. Supabase supports email OTPs; its email template must be configured to send a code rather than the default magic link.

Passwordless email documentation

Authentication ≠ authorization

Authentication: “Which signed-in account is making this request?” The email sign-in link establishes a session.

Authorization: “May this account change this calendar now?” Being signed in does not give someone ownership of every calendar.

A guest link is a separate access credential. Anyone receiving a forwarded link inherits its guest permissions. Anonymous guests cannot be individually identified or reliably attributed.

Implementation choices: the deadline is December 1 at 00:00 UTC for each calendar’s year. Movie editing freezes for everyone. Owners retain deletion and guest-link revocation for control over their data; these are separate from changing movies. This distinction is visible in the app and can be adjusted if the intended product policy differs.

What happens between fetch() and the screen changing?
  1. The browser sends a request to a URL, using a method, headers and sometimes a body.
  2. The server checks credentials, permissions, size limits and values.
  3. The database accepts or rejects the operation.
  4. The API returns an HTTP status and JSON response.
  5. The browser checks response.ok, reads the JSON, then shows success or a useful error. A 400 or 500 response does not automatically make fetch() reject.

An additional 409 Conflict can prevent one editor from overwriting another editor’s newer version. Definitions: MDN HTTP status codes.

How to investigate a real failure: open the browser’s Network tab, reproduce it, select the API request and record the method, URL, status and redacted body. Find its request ID in server logs. Compare the logged permission or validation failure with the UI message. Never publish session tokens, email sign-in links or guest links in screenshots.

05 / TRUST, SECRETS & HOSTING

Simple for people.
Strict with requests.

The browser belongs to the person using it. They can change JavaScript, inputs and local storage or send requests directly. Server-side checks are what make the proposed sharing rules trustworthy.

Validate the whole change

Require a valid calendar ID, a day from 1 to 24 and a trimmed title of 1–120 characters. Limit payload sizes, reject unexpected owner or permission fields, and validate a full list for missing or duplicate days.

Check access and write in one transaction. A deadline or lock check followed by a separate unprotected write could race with another change.

Separate public config from secrets

In Vite, variables prefixed with VITE_ can enter the browser bundle. A Supabase project URL and publishable key are public configuration; service-role keys and mail credentials are not.

Use .env locally, ignore secret files in Git, commit placeholders in .env.example and use protected host settings in deployment. Next.js has a similar public prefix, NEXT_PUBLIC_.

Vite environment variables · Supabase API keys

Access rules and database defence

Use the verified user ID, not a browser-supplied owner ID. If tables are exposed through Supabase’s Data API, enforce Row Level Security and restrict function privileges. A privileged server client can bypass RLS, so its own authorization checks are essential. Do not allow direct browser writes to bypass the calendar rules.

Supabase RLS · Securing Edge Functions

Protect email sign-in links and guest links

Use expiring, single-use email sign-in links and rate-limit sending and verification. Guest links should contain long random tokens, be revocable and never act as owner credentials. Store a hash of each guest token, avoid placing tokens in logs and avoid leaking links through referrers or analytics.

Rate-limit API writes as well as authentication. Consider stronger bot protection if abuse becomes a problem. Email access recovery depends on continued access to the mailbox.

Keep errors useful without exposing secrets

Return a safe message and a request ID. Record the operation, status and ID in server logs rather than raw headers or request bodies. Avoid stack traces and database credentials in responses. If a real secret leaks, revoke or rotate it immediately, update deployed settings and investigate usage; deleting the line from the latest commit is not enough.

Could an AI movie-suggestion feature be added?

It is optional and not needed for the chosen scope. If added, Vue would ask a server endpoint for suggestions; the server would hold the provider key, validate input and apply usage limits. Verify that the key is absent from built JavaScript and Network responses. Adding an AI provider introduces extra cost and data-handling decisions.

PROPOSED INTERFACE COPY · LOCAL PREVIEW

Loading your Christmas calendar…

Keep the page layout steady while the server responds. Don’t flash default movies as though they are the saved list.
When to fetch, refresh and cache

Fetch on opening a calendar and after a successful change. Revalidate when returning to the tab, and offer a Refresh action. A modest polling interval could support shared editing without a live subscription initially.

Cache static assets. Start with Cache-Control: no-store for permission-sensitive API responses. A stale screen may show an outdated button, but the server must still reject a disallowed write. Do not overwrite an unsaved editor draft during background refresh; detect a version conflict when saving.

Accessibility and recoverable errors

Keep every control keyboard-accessible and clearly labelled. Explain a lock in text, rather than colour alone. Use a status announcement for loading and save results. Preserve a failed draft, allow retry, and disable repeated submission while a save is pending.

Do locked doors really keep the movies secret?

In the original app the complete default list is bundled in movies.ts; a closed door is a presentation rule. If future movies must be surprises for viewers, the server should omit unreleased titles from their responses. Editors who already saw the list cannot be made to forget it. The new server withholds future stored titles from read-only viewers. The default suggestions still ship in the client as draft choices; edited database titles are not bundled.

What the AI got wrong

The API initially expected the full external URL path, but Supabase removes /functions/v1 before invoking the handler. A hosted request returned 404; normalizing the path fixed it, and an unauthenticated list request then correctly returned 401. The AI also assumed email templates could be edited without custom SMTP. The dashboard showed this was unavailable, so the app now uses the default email sign-in link.

The first proposal allowed owner edits during December; the user corrected it to freeze everyone’s movie choices. A private owner link was considered, then rejected in favour of email sign-in links with recoverable access.

The scope was initially misunderstood: the old applications must remain intact, but a separate back-end application is needed. This implementation now lives in a new project rather than changing the old work.
